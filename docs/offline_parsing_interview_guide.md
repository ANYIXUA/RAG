## 一、90 秒项目介绍

> 这个项目的离线解析模块负责把 PDF、Office、HTML、CSV、JSON、字幕等资料转换为可检索的知识。文件先经过治理检查，再按格式调用解析器，统一成带文本和 metadata 的解析结果。系统随后生成 ParsedBlock，保留章节、页码、类型和前后关系；Chunker 基于 block 继续切片并加入重叠，最后调用 embedding 模型，把文档和 chunks 写入 PostgreSQL/pgvector，同时更新 manifest 和刷新报告。
>
> 当前增量判断发生在解析之后，所以未变化文件仍会重新解析，只会跳过后续切块、向量化和写库。PDF 当前以整份文档选择主要复杂解析路线，OCR 作为回退；这在混合 PDF 和半结构化表格上存在正文丢失风险。我的优化方向是逐页、逐区域解析，增加分层缓存、质量隔离、版本化发布和按 chunk 复用向量，并用固定 badcase 验证字段和值的关系，而不是只检查关键词是否出现。

这个回答已经包含职责、主流程、当前限制和改进方向。面试官继续追问时，再展开下面的题目。

## 二、主流程与数据结构

### 题 1：一份 PDF 从进入系统到完成入库，经过哪些阶段？

**你的回答**

> 解析 → 清洗 → 分页、打标签 → 切块 → 入库；质量不合格在清洗阶段拦截并进入死信队列。

**需要补充**

1. “分页、打标签”应说明为构建 `ParsedFile / ParsedBlock`；
2. Chunk 后还有向量化；
3. 清洗和质量门禁是两种职责；
4. 内容 badcase 应进入待复核/隔离流程，死信队列主要承接重试耗尽的执行任务。

**推荐回答**

> 文件先经过发现和治理预检查，再按文件类型及 PDF 特征选择解析路线。解析器输出先统一格式，然后进行文本和版面清洗，构建带页码、章节和类型的 ParsedBlock。质量门禁在昂贵的切块、向量化和正式入库之前执行；合格结果按 block 切为 chunk，生成向量，幂等写入数据库，最后更新 manifest、报告和构建状态。不合格的解析结果进入 badcase 待复核区，可重试的系统错误耗尽重试后才进入死信队列。

**当前实现**

- [`load_with_report()`](../rag_app/ingestion/loaders.py#L64) 负责目录加载和单文件异常记录；
- [`parse_document_file()`](../rag_app/ingestion/parsing.py#L97) 生成统一文档；
- [`refresh()`](../rag_app/indexing/offline.py#L48) 串联质量门禁、增量判断、切块、向量化、写库和 manifest。

### 题 2：ParsedBlock 和 Chunk 有什么区别？为什么不直接切解析后的全文？

**你的回答**

> ParsedBlock 负责把大段结构化文本组织成树状结构，Chunk 对每个分支继续细分。直接切全文可能导致语义割裂。

**补充点**

这个理解抓住了职责，但当前 `ParsedBlock` 不是一棵真正嵌套的树，而是扁平列表，通过 `parent_block_id`、`section_path`、`previous_block_id`、`next_block_id` 等字段表达关系。

**推荐回答**

> ParsedBlock 是解析后的结构中间层，表达标题、段落、列表、表格、页码和章节关系；Chunk 是面向检索和 embedding 的大小受控文本单元。先构建 block 再切 chunk，可以减少跨章节混切，并把章节和来源信息带入检索。当前实现仍可能在一个较长 block 内按窗口切开，所以它只是降低语义割裂风险，不能保证语义永远完整。

代码：[`chunking.py`](../rag_app/indexing/chunking.py#L85)、[`chunking.py`](../rag_app/indexing/chunking.py#L132)。

### 题 3：`chunk_size=800`、`overlap=120`，1200 个连续字符怎样切？

**你的回答**

> 第二片应该从第 681 个字符开始；从第 801 个开始可能影响召回率。

**推荐回答**

> 第一片是第 1～800 个字符，第二片从第 681 个字符开始到第 1200 个字符，两个窗口重叠 120 个字符。重叠可以降低关键语句刚好被切断的概率，但会增加向量数量、存储和重复召回，因此不能把 overlap 当成召回率保证。

注意：当前切片单位根据文本特征选择字符或空白词，并不是 embedding 模型的真实 tokenizer token。代码：[`chunking.py`](../rag_app/indexing/chunking.py#L198)。

## 三、增量构建与缓存失效

### 题 4：文档内容没有变化，是否需要重新调用向量模型？

**你的回答**

> 不需要，因为切块内容没有改变。

**推荐回答**

> 如果最终传给 embedding 模型的 chunk 文本和 embedding 模型身份都没变，向量可以复用。只改权限、业务标签等 metadata 时，应更新存储中的 metadata，不需要重新生成向量。判断时不能只看原文件哈希，还要看解析、清洗和切块是否最终改变了 chunk 文本。

**当前实现与改进边界**

- 当前未变化文档会跳过后续 embedding；
- 但判断发生在解析完成之后，仍然会重新解析文件；
- 当前没有按 `chunk_text_hash + embedding_fingerprint` 复用部分向量的缓存。

### 题 5：修复了解析逻辑，以前丢失的表格现在被提取出来，是否需要重新向量化？

**你的回答**

> 需要重新切片并重新向量化。解析结果变化后文档哈希会变化。

**推荐回答**

> 需要。解析结果增加了以前丢失的表格，ParsedBlock 和 chunk 文本会发生变化，原向量不能表达新增信息。系统应根据 parser version、配置指纹和解析输出哈希使缓存失效，然后重新清洗、构建 blocks、切片并为发生变化的 chunks 生成向量。

### 题 6：当前增量处理实际节省了什么？

**你的回答**

> 没有更新的文档不会重新解析入库。

**需要修正**

当前代码先完成目录加载和解析，再比较 manifest，所以它**仍会重新解析**。实际节省的是未变化文档的切块、embedding 和数据库写入。

代码：[`offline.py`](../rag_app/indexing/offline.py#L64)、[`offline.py`](../rag_app/indexing/offline.py#L81)。

### 题 7：怎样优化到“未变化文件不重新解析”？

**推荐回答**

> 在昂贵解析前计算源文件字节哈希，并把它与解析器指纹一起作为 ParsedFile 缓存键。缓存命中后仍要重新应用必须实时生效的治理和权限规则，不能把缓存命中误判为源文件消失。解析、清洗、block、chunk 和 embedding 各自使用独立版本或指纹，哪一层变化就从哪一层向下重新计算。

建议的分层身份：

```text
source_hash
parser_fingerprint
cleaner_version / cleaned_output_hash
chunker_fingerprint
chunk_text_hash
embedding_fingerprint
```

这是**改进方案**，当前仓库没有分层缓存。

### 题 8：PDF 没变，但清洗规则修复了一个 bug，哪些结果可以复用？

**你的回答**

> PDF 解析结果可以复用，清洗和后续步骤重新执行。

**补充点**

清洗必须重新执行，但昂贵的后续步骤仍可根据新输出继续判断：

- 新清洗结果与旧结果完全相同：blocks、chunks 和向量可以继续复用；
- 文本或结构变化：重建 blocks 和 chunks；
- 最终 chunk 文本变化：重新生成对应向量。

### 题 9：外部 OCR/MinerU 静默升级模型，本地 parser version 没变，怎样做指纹？

**本轮结论**

建议将 provider、解析路线、适配器版本、实际模型/引擎 revision、接口版本和有效配置序列化后计算指纹，同时保存原始字段用于追溯。

必须说明边界：如果服务方不返回真实模型 revision，本地无法自动发现静默升级。只能通过固定版本接口（如果存在）、缓存有效期、抽样重跑 badcase 或人工提升 cache epoch 降低风险，不能声称完全可追溯。

## 四、数据更新与一致性

### 题 10：更新文档时，怎样避免先删旧数据后写新数据失败？

**你的回答**

> 删除前把旧 chunks 放进缓存，删除旧数据；新数据成功后用新数据覆盖缓存。

**需要补充**

缓存只是备份，还必须定义失败后的恢复动作。更稳妥的 PostgreSQL 答案是：

> 先在数据库事务之外完成解析、切块和 embedding。所有新数据准备好后，在一个数据库事务内停用/删除旧版本并写入新版本；事务提交成功后再更新 manifest。如果使用版本化发布，则新版本构建并验收完成后切换 active version，旧版本暂时保留用于回滚。

**当前实现**

当前先删除旧数据，再切块和 embedding；删除和 upsert 使用两个连接事务，manifest 又是独立文件写入，不是一个原子操作。代码：[`offline.py`](../rag_app/indexing/offline.py#L126)、[`vector_store.py`](../rag_app/indexing/vector_store.py#L122)、[`vector_store.py`](../rag_app/indexing/vector_store.py#L133)。

### 题 11：Milvus 也按 PostgreSQL 的方式更新吗？

**推荐回答**

> 不能直接套用 PostgreSQL 的多语句事务。完整知识版本更适合写入新 collection，验证和加载完成后再让稳定 alias 指向新 collection，并保留旧 collection 用于回滚。文档级更新可以使用 `document_id + version` 并由应用控制 active version。单纯 upsert 同一主键不能删除新版本中已经不存在的旧尾部 chunks；chunk ID 变化时也要显式处理旧版本可见性。

### 题 12：文档哈希能否防止重复入库？

**你的回答**

> 对文档整体进行哈希一致性确认；每条 chunk 有 chunk_id 和哈希，相同就不重复写入。

**推荐回答**

> 文档哈希用于识别内容版本，但不能单独解决两个 worker 同时“先查后写”的竞争。幂等写入需要稳定生成的 chunk_id、数据库唯一约束和 upsert。这样同一任务重复执行，数据库最终仍只有一条对应记录。

当前 `chunk_id` 由 `document_id + chunk_index + chunk_text` 计算，pgvector 表使用冲突更新。代码：[`chunking.py`](../rag_app/indexing/chunking.py#L217)、[`vector_store.py`](../rag_app/indexing/vector_store.py#L296)。

### 题 13：有文档结束标记，就能证明全部 chunks 已入库吗？

**你的回答**

> 读取到文档结束标记，说明文档已经全部入库。

**需要修正**

如果它只是最后一个 chunk 的标记，就不能证明中间批次都成功。并发写入时，第 100 个 chunk 可能成功，而第 61～80 个失败。

**推荐回答**

> 构建开始时记录 `document_version`、预期 chunk 清单或数量以及 `building` 状态。协调者确认该版本所有预期的唯一 chunk ID 都已经提交后，再把状态改为 `completed`。检索只读取 completed/active 版本。完成状态是全量校验的结果，不能由最后一个 chunk 单独决定。

当前项目没有 chunk 级 `is_last/end_marker/completed`。一次 pgvector upsert 使用同一事务；“每 20 个 chunk 单独提交”只是扩展面试场景。

## 五、badcase、质量门禁与验收

### 题 14：解析后发现操作步骤丢失、表格字段和值错位，怎样定位？

**你的回答**

> 先提取 badcase，检查哪些页面步骤丢失、哪些字段和值错误；缺失步骤尝试 OCR，再转 MinerU，仍不好就人工维护；表格单独优化解析逻辑。

**需要补充**

先定位内容在哪一层消失，再决定是否换解析器：

```text
PyMuPDF 原始页文本
→ 清洗后页文本
→ 路由选择和解析器输出
→ ParsedFile
→ ParsedBlock
→ Chunk
```

如果原始文本已经有操作步骤，先检查清洗、路由替换和 block 构造；直接 OCR 可能无法修复后续逻辑丢失。

项目里已确认的风险是：`rules_ml` 只保留半结构化字段行，并可能用这些行替换整份 PDF 的结果，使原本存在的普通步骤消失。代码：[`parsing.py`](../rag_app/ingestion/parsing.py#L1096)、[`parsing.py`](../rag_app/ingestion/parsing.py#L1125)。

### 题 15：badcase 重新测试通过，就足够验收吗？

**你的回答**

> 把 badcase 作为验收依据，重新测试通过后验收；保存错误码、含义、metadata 和报错场景，人工对照 PDF。

**推荐回答**

> badcase 应建立人工确认的黄金结果，验证字段和值的对应关系、表格行列、来源页和必须保留的步骤。修复后既要跑固定 badcase，也要跑普通 PDF、扫描件和其他表格的回归样本。只有 badcase 修复且正常样本没有退化，才能验收。

例如，下面两组关系必须逐对匹配：

```text
E203 → 地址校验失败
E504 → 下游接口超时
```

四个关键词都出现但两组含义互换，仍然失败。

### 题 16：质量不合格的结果进入死信队列是否合适？

**推荐回答**

> 解析任务因为 503、超时等可恢复执行错误而反复失败，达到上限后进入死信队列。解析器已经成功返回、但内容质量不合格，属于质量 badcase，应进入隔离区或人工复核队列，并可尝试备用解析路线。两类状态、负责人和重放条件不同。

**当前高风险边界**

当前流程先做质量门禁，再用通过门禁的来源集合判断删除。已经入库的文档如果本轮质量不合格，可能被误判为来源删除并清除旧向量。正确目标应是隔离新结果、保留旧的已发布版本。代码：[`offline.py`](../rag_app/indexing/offline.py#L72)、[`offline.py`](../rag_app/indexing/offline.py#L86)。

## 六、批量解析、超时和重试

### 题 17：100 份 PDF，第 17 份异常，怎样保证后续文档继续？

**你的回答**

> 记录第 17 份的文档名称、解析器版本和异常，继续处理后面的文档，最后输出异常信息。

**推荐回答**

> 以单文档为任务隔离异常。失败记录至少包含 source、任务 ID、解析器/模型版本、错误类型、错误详情、尝试次数和时间；批次继续处理其他文档，结束后汇总成功、质量拒绝和执行失败。失败是否重试要根据错误分类决定。

当前 loader 已经捕获单文件异常并继续，但失败记录只有 `source / reason / detail`，且处理是串行的。代码：[`loaders.py`](../rag_app/ingestion/loaders.py#L76)。

### 题 18：OCR 一直卡住但不抛异常，异步和 try/except 能解决吗？

**你的思路**

> 异步调用后继续后续文档；使用任务队列和令牌，令牌失效时退出并释放资源。

**需要补充**

异步只让调用者不等待，并不会终止卡死任务。令牌属于协作取消，只能在代码重新获得执行权并检查令牌时生效；如果卡在一次 OCR 或底层子进程中，就不会及时检查。

**推荐回答**

> 将可能卡死的单文档 OCR 放入可终止的独立子进程，由父进程监督时间和并发。先请求正常取消，超过期限仍不退出时终止该进程及其子进程树。父进程确认退出后清理任务临时目录、记录超时并释放并发名额。不能依赖被强制终止的子进程一定执行 finally。

这是**改进方案**，当前项目没有持久 worker 或进程级超时隔离。

### 题 19：503、损坏 PDF、质量不合格分别怎样处理？

**你的回答**

- 503：稍后重新调用；
- 损坏 PDF：记录失败，不重试；
- 质量不合格：标记 badcase，不入库。

**推荐回答**

> 503 属于暂时性故障，使用有上限的退避重试；确定损坏的文件属于永久故障，记录后停止同路线重试；返回成功但质量不合格属于内容质量问题，不发布，进入 badcase 复核或备用解析路线。三类错误不能使用同一重试策略。

### 题 20：重试间隔和上限怎样设计？

**你的回答**

> 2、5、10 分钟重试，达到上限后进入死信队列。

**补充点**

- 首次执行加三次重试，总共最多四次尝试；
- 增加少量随机抖动，减少大量任务同一时刻重新请求；
- 死信记录应保存失败原因、次数、版本和人工重放条件，不能只是另一个无人处理的队列。

## 七、混合 PDF 和复杂版面

### 题 21：120 页 PDF 混合普通文本、扫描页和表格，怎样路由？

**你的回答**

> 先全部按普通文本识别，标记识别率不高的页面；表格页走表格流程，图片页走 OCR。

**推荐回答**

> 先用 PyMuPDF 对所有页面做低成本基础提取，同时计算文本质量、图片占比、边框、列对齐和表格特征。普通区域保留基础结果，扫描区域走 OCR，表格区域走对应解析器；复杂解析失败时保留基础文本并记录告警。最后按真实页码和区域阅读顺序合并。

不能只看文本长度判断表格。表格页可能提取出很多文字，但字段和值关系已经损坏。

**当前实现**

当前对整份 PDF 选择主要复杂解析路线，不是逐页、逐区域混合路由。代码：[`parsing.py`](../rag_app/ingestion/parsing.py#L507)。

### 题 22：同一页上方是步骤、下方是表格，怎样避免步骤丢失？

**你的回答**

> 从表头开始扫描，把表放到一个新页面。

**需要修正**

可以把表格放入独立的逻辑 block，但不能创建虚假 PDF 页码。表头也不能单独决定完整表格边界。

**推荐回答**

> 保留页面元素的 bbox，识别表格区域后，只把该区域交给表格解析器；普通提取结果排除相同区域，避免重复。随后按纵向位置恢复“上方段落—表格—下方段落”的顺序。三个元素都保留原始 page number，表格作为 table 类型 ParsedBlock。

当前 ParsedBlock 模型预留了 bbox，但主 PDF block 构造没有完整填入它。这是改进方向，不是当前能力。

### 题 23：跨页表格怎样识别？

**本轮回答**

> 这部分不会，记录下来，后续 demo 加上。

**面试时可以先回答边界，再给设计**

> 当前项目没有跨页表格拼接能力，我会把它作为明确限制说明。设计上会综合判断页相邻、前页表格靠近页尾、后页候选区域靠近页首、列数量与宽度、表头/列类型相似度以及续表标记。确认续表后使用稳定 table_id 合并，但每一行仍保留真实 source page。当列结构明显变化或出现普通段落时终止合并。这个方案需要固定 badcase 验证，不能只靠一个表头规则。

后续 demo 的固定案例：前页有表头、后页无表头、后页表格结束后还有普通段落；要求不丢行、不重复、正文不被吞并、每行来源页可追溯。

### 题 24：双栏页面怎样恢复阅读顺序？

**你的回答**

> 先识别边栏，按照从上到下、从左到右整理成单栏。

**补充点**

必须先分栏再排序。如果对全页直接执行“先 y 后 x”，同一高度的左右栏仍会交叉。

**推荐回答**

> 根据文本块 bbox 和横向间距聚类成列，全宽标题单独作为区域；每栏内部从上到下排序，再按左栏、右栏合并。保存原始 page、bbox、column index 和 reading order，方便引用和排查。

### 题 25：怎样过滤重复页眉、页脚而不误删安全警告？

**你的回答**

> 在数据清洗阶段用正则过滤，页眉页脚相对于正文的位置固定。

**推荐回答**

> 在仍保留 bbox 的页面元素阶段先圈定顶部、底部候选区域，再结合跨页重复和正则识别固定标题、页码等模板噪声。删除动作只作用于候选区域，不能对全文做全局替换。正文中的同名标题和安全警告使用保留规则；对不确定项宁可留下并记录，也不静默删除业务内容。

## 八、解析器适配层

### 题 26：PyMuPDF、OCR、MinerU 输出格式不同，在哪一层统一？

**你的回答**

> 在数据清洗层统一，清洗完成后保存，方便复用。

**推荐回答**

> 每个解析器先通过 adapter 转换成统一的 ParsedFile 或 PageElement；清洗层只消费统一对象，不写 `if OCR / if MinerU` 的分支。统一对象至少保留 text、page number、block type、bbox、parser/engine version、confidence、warning 和 source metadata。清洗后的中间结果可以缓存，但缓存键必须包含 cleaner version。

当前代码已经部分采用 adapter → ParsedFile → ParsedBlock 的方向，但没有持久化完整的中间结果缓存。

## 九、个人复习重点

### 已经掌握较好的部分

- ParsedBlock 与 Chunk 的职责；
- overlap 的窗口计算和召回影响；
- 内容不变时无需重新生成向量；
- 解析结果变化时需要从对应层向下失效；
- 使用 badcase 定位丢失步骤和字段值错位；
- 单文件异常不应阻断整个批次；
- 503、损坏文件、质量 badcase 的分类；
- 递增重试与死信队列；
- 稳定 chunk ID 和文档哈希用于幂等判断。

### 面试前还要补熟的部分

- `try/except`、异步、协作取消和进程隔离各自能解决什么；
- 为什么哈希预检查不能替代数据库唯一约束和 upsert；
- 为什么最后一个 chunk 存在不能证明文档完整；
- 清洗、质量门禁、badcase 队列和死信队列的职责边界；
- 页面级与区域级 PDF 路由；
- 跨页表格的连续性特征和停止条件；
- 外部解析模型不暴露 revision 时无法做到完全可追溯。

## 十、面试易错表达

| 不够准确的说法 | 更准确的说法 |
| --- | --- |
| 文件没变就不会重新解析 | 当前仍解析，只跳过后续切块、向量化和写库；分层解析缓存是改进方案 |
| ParsedBlock 是一棵树 | 当前是带层级和前后关系字段的扁平 block 列表 |
| chunk size 是 token 数 | 当前是字符或空白单元，不是模型 tokenizer token |
| 异步可以终止卡死 OCR | 异步只能释放调用方等待；强终止需要进程隔离和父进程监督 |
| 哈希相同就绝不会重复入库 | 还需要确定性 ID、唯一约束和 upsert |
| 看到最后一个 chunk 就完整 | 必须校验本版本全部预期 chunk 后设置 completed |
| badcase 都放死信队列 | 内容质量 badcase 进入复核隔离；执行重试耗尽才进 DLQ |
| 表格单独放到新页 | 生成独立逻辑 block，但保留真实 PDF 页码 |
| 正则就能过滤页眉页脚 | bbox 候选区域、跨页重复、正则和保留规则共同判断 |
| Milvus 和 PostgreSQL 一样做事务 | Milvus 需要版本、collection/alias 或应用可见性策略 |
| 当前支持跨页表格 | 当前不支持；这是待完成 demo 和设计目标 |

## 十一、30 秒收尾回答

> 我会把离线解析看成一个分阶段、可验证的构建流程，而不是一次从 PDF 到向量的黑盒转换。每一层都有稳定输入、版本指纹、质量状态和可追溯输出；出现 badcase 时先定位内容在哪一层丢失，再决定换解析器或修逻辑。发布时只让通过质量门禁且构建完整的版本可见，并通过稳定 ID、唯一约束和版本状态保证重试幂等。当前项目已经有 ParsedBlock、质量门禁、增量 manifest 和 pgvector upsert，逐页区域路由、分层缓存、进程隔离和跨页表格仍是后续改进方向。
